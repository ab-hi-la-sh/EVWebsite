The details that matter when you are building for the AI world.

How tokens behave, what gets logged, and what happens when something fails.

Deterministic tokenization
The same plaintext always produces the same token. “John Smith” in message 1 and message 10 map to the same [NAME: Ry0Ixd1] token, preserving cross-message context without ever exposing real data to the model.
Context phrase neutralization
NoPII does not just mask values. It neutralizes data-type labels that could trigger model safety refusals or re-identify sensitive categories. Social security number becomes ID number, credit card number becomes account number, date of birth becomes date, so the model processes tokens without recognizing the underlying data type.
Fail-safe architecture
If detection encounters an error, the proxy blocks the request rather than letting unprotected data through. Every decision is logged for audit.
Streaming support
Standard and streaming SSE responses are both supported. Token replacement happens on the fly as chunks arrive, so latency impact is minimal even for long streaming completions.
Configurable token retention
Vault tokens carry a time-to-live that controls how long tokenized data is stored. Tokens expire after one day on Lite and after 30 days on Starter. Growth and Business can keep them up to permanently, and Enterprise sets custom retention. When a token expires, the underlying data is permanently deleted from the vault.
Secret and API key detection
Cloud provider keys, model API keys, payment and code-platform tokens, database connection strings, private keys, and auth tokens are detected across 14 pattern families, replaced with vault tokens, restored in the response, and logged in the audit trail. On by default for new accounts.
Reveal policy
A token is revealed only to the end user who created it, within a session that belongs to no one else, under a time-boxed reveal grant, or by a server key with an opt-in scope. Every reveal attempt is logged, refusals included. If the reveal cache is unavailable, reveals are refused, not allowed. How the reveal policy works.
The log is not a second leak
Audit entries record the token, a masked form of the value, entity type, confidence, session, provider, model and timestamp. Plaintext is never written to the log. Purging a token for an erasure request keeps the entry, stamps it with purged_at and purged_by, and leaves nothing it can resolve to.
Drop-in authentication
There is no NoPII-specific header or key to add. Register your OpenAI, Anthropic or other provider key once in the console; NoPII recognizes it on every request, routes to the right provider, and passes it through. Multiple providers can be registered under one account, each independently mapped, with one audit log across all of them.
Observability
Langfuse tracing is opt-in per workspace and records tokenized content only, never plaintext. NoPII honors the W3C traceparent header for distributed tracing through OpenTelemetry context propagation. Tracing failures never affect proxy requests. Available on Growth and above. Tokenizing is safe to allow widely. Revealing is not.

A token turns back into plaintext only for the user it belongs to, and every attempt, including every refusal, is logged.

When a token is created, NoPII records who created it. A later reveal is allowed only when one of four conditions holds. Anything else is refused, per token, and the SDK leaves the token in place or shows a placeholder you choose. If NoPII’s shared cache is unavailable, reveals are refused rather than allowed: an outage can cost a user their own history view, never another user’s data.

  1. The caller’s end user created the token.
  2. The token was created in the session the caller names, and that session belongs to no other user.
  3. The caller presents a reveal grant that covers the token.
  4. The caller’s key has the detokenize-any scope, which is opt-in and server-side only.

Reveal grants Business and above

Temporary permission to reveal tokens the caller does not own, for support tools and other cross-user views. Minted by your server with a secret key, scoped to one user or a token list, 60 seconds to one day, with a recorded reason such as a ticket number.

Reveal log Business and above

Every reveal attempt, one entry per token, refusals included: outcome, end user, key or session, client IP and the grant if one was used. Repeated refusals are how probing shows up.

Three key kinds

Secret keys live on your servers only. Publishable keys are origin-restricted and embedded in a page. Device keys are issued by enrollment. Privileged scopes requested for a publishable or device key are dropped, not granted.

The four conditions apply wherever the client API is available, on Starter and above.

The vector database is a second copy of your customer data.

Every document you embed becomes an input to a provider’s embeddings API. NoPII tokenizes it first, so the index holds tokens and search still works.

RAG pipelines embed support tickets, case files, contracts and clinical notes in bulk, and each one is an API call to a model provider. The identifiers go with it. NoPII proxies the embeddings endpoint the same way it proxies chat: every text in the request is tokenized before it reaches the provider, and the vectors come back exactly as the provider produced them. There is nothing in a vector to restore, so nothing is added to the request and the provider’s token count is entirely your own content.

Because tokens are deterministic, the same name or email becomes the same token in every document and every query. A search for a customer’s record finds every document that mentions them, because the name works as a consistent keyword. What changes is only that the provider never held it.

  • Available for keys registered with OpenAI, Mistral, Together, Fireworks and Gemini, whose APIs serve an embeddings endpoint.
  • Tokens carry nothing of the value they replace, so similarity between two tokenized names says nothing about how alike the names are. Match and deduplicate names on your side before they reach the proxy; use NoPII embeddings for search over documents that mention people.

The questions an engineer asks next.

Streaming and multi-turn token restoration

SSE responses detokenize in flight, so real-time chat keeps streaming. Deterministic tokens keep multi-turn conversations coherent: the same person is the same token across every turn of the session.

Why tokens, not redaction

NoPII restores its own tokens on the way back, so your application receives real values in the response. Placeholder redaction destroys the entity relationships a model needs to reason. Tokens preserve structure in both directions, which is the only approach that protects data without breaking the model.

Agents, tool calls and the Responses API

NoPII scans every text field a model can read or write: user and assistant messages, the system prompt, function call arguments and the tool results you feed back. The OpenAI Responses API is served alongside Chat Completions, and Anthropic tool use and tool results are sanitized in the Messages endpoint. Streamed tool call arguments are held until the call completes and released as one piece, so a token split across chunks never breaks the JSON your agent is parsing.

Tracing without exposure Growth and above

With Langfuse enabled, every proxied request produces a trace with three spans: sanitize, the LLM call, and desanitize. Your questions about NoPII, answered.

Privacy and tokenization

What is NoPII?
NoPII is a PII-tokenizing reverse proxy for LLM APIs, built by Enigma Vault. It sits between your application and model providers, detects sensitive data across 30+ configurable entity types, tokenizes it before it reaches the model provider, and detokenizes responses on the way back. Your application works with real data; the provider only ever sees tokens.
How is tokenization different from redaction or masking?
NoPII restores its own tokens in the response, so your application receives real values back. Placeholder redaction replaces sensitive values with text that destroys the relationships a model needs to reason. NoPII tokenizes deterministically: the same value always maps to the same token, so reasoning stays intact, and round-trip detokenization returns real data to your application. Tokens preserve structure in both directions; redaction preserves it in neither.
What happens if detection or tokenization fails?
The request is blocked, not forwarded. NoPII is fail-safe by default: sensitive data never proceeds on a best-effort basis. The block is logged so your team sees it immediately. This is architecture, not a configurable setting.
Does it catch API keys and secrets, not just personal data?
Yes. Fourteen credential pattern families are detected in the same pass as PII: cloud provider keys, model API keys, payment and code-platform tokens, database connection strings, private keys, and auth tokens. Detected secrets are replaced with vault tokens, restored in the response, and logged in the audit trail. It is on by default for new accounts.
How accurate is detection?
Detection covers 30+ configurable entity types and is validated in a published 109-test report. Detection sensitivity is adjustable, and custom phrase rules are available on paid plans.
Does NoPII support HIPAA and GDPR workloads?
Yes. It is built for HIPAA, GDPR, CCPA, and PCI DSS requirements, with BAA availability for healthcare deployments and request-level audit logs for every transaction. Right-to-erasure resolves at the vault level, because identifiers never reach provider logs in the first place, and token purge deletes every token for a list of values in one request.
Does NoPII protect consumer chatbot websites?
No. NoPII protects application traffic that is routed through its proxy. If your application calls an LLM API through the NoPII base URL, every request and response on that path is covered. Traffic that never passes through the proxy, such as an employee pasting data into a consumer chatbot website in their browser, is outside its scope.
Does NoPII only protect the model provider, or my servers too?
Both, depending on tier. The proxy keeps plaintext away from the provider. The browser SDK, in preview, tokenizes in the user’s browser so your backend and logs hold only tokens and the reply is revealed only to the user it belongs to.
Does NoPII detect identifiers outside the US?
Yes. Beyond the global types, it covers India (Aadhaar, PAN, voter ID, vehicle registration, Hindi names and addresses), the UK (National Insurance, NHS), Spain, Italy, Poland, Finland, Australia and Singapore. Regional types are off by default and switched on per workspace. Several are in beta.
Does NoPII scan images, audio or files?
No. NoPII scans text: messages, system prompts, tool call arguments and tool results. Images, audio, files and documents are not scanned, so extract the text from a document before it goes to the model if it needs protecting.
